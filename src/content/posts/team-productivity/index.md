# 개인의 생산성에서 팀의 생산성으로

나 혼자 빠르게 개발하는 것보다 팀 전체가 잘 일할 수 있는 환경을 만드는 일에 대해 생각해봤다.

개발을 시작했을 때는 내가 잘하는 것이 중요했다. 코드를 잘 작성하는 것, 기능을 빠르게 구현하는 것, 어려운 기술적 문제를 해결하는 것. 이런 것들이 개발자로서 성장하는 기준이라고 생각했다.

하지만 함께 개발하는 시간이 길어지면서 조금씩 다른 것들이 눈에 들어오기 시작했다.

**내가 빠르게 개발하는 것과 팀이 빠르게 개발하는 것은 다른 문제였다.**

## 생산적인 개인이 생산적인 조직을 만들지는 않는다

최근 인상 깊게 읽은 글이 있다. [생산적인 개인이 생산적인 기업을 만들지는 않는다](https://news.hada.io/topic?id=30412).

이 글에서는 전기 도입기의 공장을 사례로 소개한다. 1890년대 공장은 기존의 증기기관을 전기 모터로 교체했지만, 더 좋은 기술을 도입했다고 곧바로 기대했던 생산성 향상이 나타나지는 않았다.

의미 있는 변화는 전기를 활용할 수 있도록 공장의 구조와 작업 방식을 재설계하면서부터 나타났다. AI를 도입하는 지금의 모습과도 닮아 있다.

개개인이 더 빠르게 코드를 작성하고 문서를 만들 수 있게 되었지만, 그것이 반드시 조직의 성과로 이어지는 것은 아니다.

**기술이 달라졌다면 일하는 방식도 달라져야 한다.**

## 모두가 바쁘다고 생산적인 것은 아니다

한 개발자가 하루에 다섯 개의 PR을 생성한다고 가정해보자. 하지만 코드 리뷰와 QA 단계에서 하루에 두 개만 처리할 수 있다면 어떨까?

개인의 작업 속도는 빨라졌지만 팀 전체의 처리 속도는 그대로다. 오히려 검토해야 할 코드만 계속 쌓인다.

이러한 관계는 리틀의 법칙(Little's Law)으로도 살펴볼 수 있다.

> 평균 진행 중인 업무량 = 단위 시간당 평균 처리량 × 업무가 완료되기까지 걸리는 평균 시간

업무 흐름이 안정적이고 처리량이 일정하다면, 진행 중인 업무가 많을수록 작업이 완료되기까지 걸리는 평균 시간도 길어진다.

결국 중요한 것은 각자가 얼마나 많은 일을 하는지가 아니라 **전체 업무의 흐름이 얼마나 원활한가**에 있다.

## 많이 만드는 것과 가치를 만드는 것

생산성을 이야기할 때는 산출물과 성과를 구분해서 볼 필요가 있다.

| Output · 산출물 | Outcome · 성과 |
| :--- | :--- |
| 작성한 코드의 양 | 해결한 사용자의 문제 |
| 배포한 기능의 수 | 개선된 사용자 경험 |
| 작성한 문서의 수 | 줄어든 커뮤니케이션 비용 |
| 구축한 공통 컴포넌트 | 감소한 반복 작업과 유지보수 비용 |

산출물은 무엇을 얼마나 만들었는지를 보여주고, 성과는 그것이 어떤 변화를 만들어냈는지를 보여준다.

공통 컴포넌트를 100개 만드는 것보다 팀원들이 반복적으로 겪는 문제를 해결하는 컴포넌트 하나를 만드는 것이 더 가치 있을 수도 있다. 코드를 작성하는 일 자체가 목적이 되어서는 안 되는 이유다.

## 한 번의 개선이 팀 전체의 시간을 절약한다

실무에서 디자인 시스템과 공통 컴포넌트를 구축하고 개발 환경을 개선하면서 느낀 점이 있다. 당장 내 작업만 생각한다면 필요한 기능을 직접 구현하는 편이 더 빠를 때도 있다. 하지만 팀의 관점에서는 조금 다르다.

- 공통 컴포넌트와 디자인 시스템 구축
- Storybook을 활용한 컴포넌트 문서화
- 모노레포를 활용한 공통 코드 관리
- ESLint를 활용한 코딩 컨벤션 표준화
- 반복적인 작업의 자동화

이러한 작업들은 당장 새로운 기능을 만들어 내지는 않는다. 오히려 초기에는 더 많은 시간과 노력이 필요하다. 하지만 잘 만들어진 개발 환경은 여러 개발자가 반복적으로 소비하는 시간과 비용을 줄여준다.

한 사람의 노력이 여러 사람의 생산성으로 이어지는 것이다.

## 개발자도 사용자다

제품을 개발할 때는 사용자가 겪는 불편함을 해결하기 위해 많은 고민을 한다. 그런데 정작 제품을 만드는 개발자가 겪는 불편함에는 얼마나 관심을 가지고 있을까?

- 처음 프로젝트에 합류한 개발자는 쉽게 적응할 수 있는가?
- 필요한 정보를 찾기 위해 여러 사람에게 물어봐야 하는가?
- 반복적으로 발생하는 실수를 시스템으로 예방할 수 있는가?
- 특정 개발자가 없어도 작업을 이어갈 수 있는가?

이런 문제들을 해결하는 것 역시 Developer Experience(DX)의 일부라고 생각한다. 좋은 개발 환경은 개발자가 불필요한 곳에 에너지를 소비하지 않고 중요한 문제에 집중할 수 있도록 돕는다.

## 마무리

예전에는 내가 얼마나 빠르게 개발할 수 있는지를 고민했다. 지금은 조금 다른 질문을 하게 된다.

- 내가 만든 것이 다른 개발자의 시간을 얼마나 절약할 수 있을까?
- 반복되는 문제를 구조적으로 해결할 수는 없을까?
- 나 없이도 잘 동작하는 환경을 만들 수 있을까?

개인의 역량을 높이는 것은 여전히 중요하다. 하지만 그 역량을 팀 전체의 성장으로 연결하는 것 또한 개발자의 역할이라고 생각한다.

**혼자 잘하는 개발자에서 함께 잘할 수 있는 환경을 만드는 개발자로 성장하고 싶다.**
