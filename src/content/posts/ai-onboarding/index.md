# AI도 온보딩이 필요하다

AI를 프로젝트에 도입하면서 겪었던 시행착오와 좋은 개발 환경에 대해 고민했던 것들을 정리해봤다.

새로운 팀원이 입사하면 온보딩 과정을 거친다. 프로젝트의 구조를 설명하고, 코딩 컨벤션을 공유하고, 팀이 일하는 방식을 알려준다.

그런데 처음 AI를 프로젝트에 도입했을 때는 이런 과정 없이 곧바로 작업을 요청했다. 돌아보면 이게 많은 시행착오의 시작이었다.

## 코드는 맞는데 프로젝트에는 맞지 않았다

AI가 작성한 코드 자체가 항상 잘못된 것은 아니었다. 기능은 정상적으로 동작했지만 프로젝트의 맥락을 고려하지 않은 경우가 많았다.

- 기존 공통 컴포넌트 대신 새로운 컴포넌트를 만들었다.
- 코딩 컨벤션이 일관되지 않았다.
- 기존 상태 관리 방식과 다른 방법으로 구현했다.
- 필요 이상으로 복잡한 코드를 작성했다.
- 이미 구현된 기능을 중복해서 만들었다.

코드를 작성하는 시간은 줄었지만 검토하고 수정해야 할 부분은 늘어났다. AI에게 **무엇을 구현해야 하는지**는 알려줬지만, **우리 프로젝트에서 어떻게 구현해야 하는지**는 알려주지 않았던 것이다.

## AI에게도 맥락이 필요하다

같은 기술 스택을 사용하더라도 프로젝트마다 일하는 방식은 다르다. 그래서 AI에게 전달해야 할 정보를 정리하기 시작했다.

- 프로젝트 구조와 아키텍처
- 기술 스택과 라이브러리
- 코딩 컨벤션
- 공통 컴포넌트와 기존 구현 패턴
- 작업 범위와 검증 방법

매번 같은 내용을 설명하는 대신 프로젝트의 규칙을 문서화하고 AI가 참고할 수 있도록 했다. `AGENTS.md`나 `CLAUDE.md` 같은 파일도 이 목적으로 활용할 수 있다.

모델 자체를 다시 학습시키는 것이 아니라, **작업에 필요한 맥락을 제공하는 것**이다.

## 암묵적인 규칙을 명시적인 규칙으로

코딩 컨벤션을 정리하면서 흥미로운 점을 발견했다. 생각보다 많은 규칙이 문서가 아닌 개발자의 머릿속에 존재하고 있었다.

기존 팀원에게는 당연한 규칙이지만 처음 프로젝트를 접하는 사람에게는 그렇지 않다. AI 역시 마찬가지다. 예를 들면 다음과 같은 기준을 문서로 남길 수 있다.

```markdown
# Project Rules

## Components
- 기존 공통 컴포넌트를 우선 재사용한다.
- 새로운 컴포넌트를 작성하기 전에 유사한 구현을 확인한다.

## API
- 기존 API 호출 패턴을 유지한다.
- 에러와 로딩 상태를 고려한다.

## TypeScript
- 불필요한 any 타입 사용을 지양한다.
- 기존 타입 정의를 우선 활용한다.

## Validation
- TypeScript 타입 검사
- ESLint 검사
- 관련 테스트 실행
```

중요한 것은 규칙의 개수가 아니라 명확한 기준이다. AI를 위해 시작한 문서화였지만, 결국 팀의 개발 방식을 정리하는 과정이기도 했다.

## 코드를 작성하는 것에서 작업을 관리하는 것으로

AI를 활용하면서 작업을 요청하는 방식도 달라졌다. 단순히 기능 구현을 요청하는 것이 아니라 작업의 목적과 범위, 제약 사항까지 함께 전달하기 시작했다.

```text
요구사항 정의
  → 맥락 및 작업 범위 전달
  → AI 코드 생성
  → 변경 사항 확인
  → 검증 및 피드백
```

반복적으로 발생하는 문제는 규칙에 반영하고, 자동으로 검증할 수 있는 부분은 타입 검사나 린트, 테스트를 활용했다. 코드를 직접 작성하는 것만큼 작업의 전체 과정을 관리하는 일도 중요해졌다.

## 무엇이 달라졌을까?

프로젝트의 규칙과 작업 방식을 정리하면서 몇 가지 변화가 생겼다.

- 코드의 일관성이 높아졌다.
- 같은 내용을 반복해서 설명하는 일이 줄었다.
- 코드를 검토하고 수정하는 데 드는 시간이 줄었다.
- 작업 내역과 변경 사항을 관리하기 쉬워졌다.

모든 문제가 해결된 것은 아니지만, 이전보다 AI와 함께 일하기 좋은 환경이 만들어졌다.

## 마무리

처음에는 AI를 잘 활용하려면 프롬프트를 잘 작성해야 한다고 생각했다. 하지만 실제로 경험해보니 프롬프트만큼이나 중요한 것은 AI가 일하는 환경이었다.

잘 정리된 아키텍처, 명확한 코딩 컨벤션, 일관된 개발 방식, 자동화된 검증 과정. 생각해보면 모두 좋은 Developer Experience(DX)를 위해 필요한 것들이다.

**AI가 잘 일할 수 있는 환경은 결국 개발자도 잘 일할 수 있는 환경이 아닐까.**

AI를 도입하면서 오히려 좋은 개발 환경에 대해 더 많이 고민하게 됐다.
